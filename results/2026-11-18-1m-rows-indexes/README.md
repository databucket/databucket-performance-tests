# 1M rows: without and with indexes on the properties (2026-11-18)

**Question:** how much do expression indexes on the JSON properties used in the rules help a bucket with 1 million
rows under a mixed load, and is `plan_cache_mode = force_custom_plan` needed for PostgreSQL to use them?

**Answer:** the indexes make the whole load **~25× faster at the 95th percentile (3158 → 135 ms) and double the
throughput (59 → 113 requests/s)**. `force_custom_plan` changed nothing in this load (151 ms); the generic-plan problem
seen earlier (an `AND` of two properties with `LIMIT/OFFSET` in `/get`) didn't show up here.

> **Repeated** in [2026-11-18-1m-rows-tags](../2026-11-18-1m-rows-tags/README.md) with `VACUUM FULL` before every run:
> the table had many dead rows here, which made the reservation slower (B: p95 135 ms, after `VACUUM FULL` 50 ms). The
> conclusions about the indexes stand.

## Setup

- Databucket 3.16.2 (master 9019098), the docker compose of databucket-server on one laptop (14 CPUs; Databucket,
  PostgreSQL 18 and Gatling on the same machine): `max-concurrent-requests` 30 (Tomcat threads = DB pool), PostgreSQL
  defaults (`shared_buffers` 128 MB).
- Data (`./gradlew prepareData -Prows=1000000`): bucket `users` with **1,000,000 users** (+ ~800 left from earlier runs),
  history on (1.2M history rows), **200,000 reserved** by the admin (20 %), table 332 MB. `VACUUM ANALYZE` before run A.
- Load, the same in all runs:
  `./gradlew gatlingRun -Pusers=100 -PrampUp=30 -Pduration=120 -Prules=premium-pl`
  - 100 virtual users (own accounts), started within 30 s, then 120 s of full load,
  - mix create 40 % / search 30 % / delete 30 %, pauses 500-2000 ms between the steps,
  - search rules `premium-pl`: `[["$.type", "==", "PREMIUM"], ["$.country", "==", "PL"]]` (~3 % of the rows), `sort=id`.
  - exact settings of each run: `settings.txt` in its folder.

| Run | Folder | What was different |
|---|---|---|
| A | [a-no-indexes](a-no-indexes/report/index.html) | only the standard indexes of a bucket (`data_id`, `(tag_id, reserved)`) |
| B | [b-indexes](b-indexes/report/index.html) | + 6 expression indexes (below), made by hand: what the "indexed properties" feature would create |
| C | [c-indexes-custom-plans](c-indexes-custom-plans/report/index.html) | B + `plan_cache_mode = force_custom_plan` for the connections of Databucket (`ALTER ROLE databucket_user SET ...`, app restarted; reverted after the run) |

Indexes of run B and C (built in 4.5 s together, ~7 MB each, 22 MB the numeric one):

```sql
CREATE INDEX "x-bucket-718_p_type"    ON "x-bucket-718" ((properties #>> '{type}'));
CREATE INDEX "x-bucket-718_p_country" ON "x-bucket-718" ((properties #>> '{country}'));
CREATE INDEX "x-bucket-718_p_origin"  ON "x-bucket-718" ((properties #>> '{origin}'));
CREATE INDEX "x-bucket-718_p_status"  ON "x-bucket-718" ((properties #>> '{status}'));
CREATE INDEX "x-bucket-718_p_group"   ON "x-bucket-718" ((properties #>> '{group}'));
CREATE INDEX "x-bucket-718_p_age"     ON "x-bucket-718"
  ((CASE WHEN jsonb_typeof(properties #> '{age}') = 'number' THEN (properties #> '{age}')::numeric END));
```

## Conclusions

1. **Searching by properties is the bottleneck of a big bucket.** Without indexes every search reads the whole table
   (`find and reserve` p50 4.1 s, `find created users` 1.8 s). They also hold the 30 DB connections that long, so even
   the steps that only touch one row by id (insert, modify, delete: ~15 ms in B) wait ~300 ms (p50) / ~700 ms (p95) in A.
2. **Expression indexes on the properties used in the rules fix it**: every step 15-20 ms at p50, throughput doubled
   (the virtual users spend less time waiting, so they do more rounds in the same time). The indexes are small and
   quick to build; their cost on writes didn't show (inserts/updates 15-20 ms in B).
3. **The SQL generated by Databucket uses the indexes as it is** (the path of the property as a bind parameter works);
   `force_custom_plan` isn't needed for this load (C ≈ B, slightly slower: more planning). It may still matter for
   `/get` with several conditions and `LIMIT/OFFSET` (seen in the 1M-row check of the same day, 230 → 39 ms) - to
   be checked with a load that pages through `/get` results.
4. **`find and reserve` stays the slowest step with indexes (p95 171 ms vs ~20 ms for the others)** - next thing to
   look at (e.g. whether the reservation counts all matching rows for `available`, or how `sort=id` + the
   rules + `reserved = false` are planned).
5. For the feature: a list of indexed properties per bucket (path + type text / number) creating these indexes is worth
   doing; the rest of the stack needs no change for them to work.
